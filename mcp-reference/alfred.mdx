title: "alfred"
description: "Vault read/write, agent delegation, Temporal workflows, briefings, decision actions, gateway diagnostics, tool dispositions, focused-subagent delegation, notifications — the Alfred control surface as 29 MCP tools."
---

The `alfred` app is the Alfred control surface for LLM clients. It surfaces the parts of ctrl-api that are safe to drive from a one-hour bearer token: read or write any vault record, kick off Temporal workflows, inspect the Hermes gateway, send notifications, and approve pending device pairings *(packages/mcp-server/src/tools/alfred.ts:18-28)*.

**Backend.** Every tool routes through `proxyToCtrl()` to ctrl-api's `/api/v1/*` endpoints *(packages/mcp-server/src/tools/alfred.ts:46-562)*. Bearer auth uses `AAS_API_KEY`. The real backends are the vault filesystem (accessed through the alfred CLI under a per-path mutex), the Temporal CLI via `docker exec`, the Hermes pairing CLI, and ctrl-api ledger queries.

**Deliberately withheld.** Restart, rotate-secret, fleet-pause, log streaming, and config-env mutation are not exposed here *(packages/mcp-server/src/tools/alfred.ts:18-28)*. Those remain available to in-tenant agents through `alfred-ctrl` where scoped trust is much higher.

<Accordion title="Vault — read, search, create, update, promote (6 tools)">

The vault surface enforces the [promotion contract](/reference/frontmatter-shapes): `create_vault_record` accepts only the 12 canonical record types. Non-canonical types (`observation`, `reflection`, `project`, `event`) are rejected by ctrl-api with HTTP 422 *(packages/mcp-server/src/tools/alfred.ts:108-113)*.

| Tool | Purpose | Key params |
|---|---|---|
| `list_vault_by_type` | List every record of a given vault type with frontmatter + body preview. | `type` (one of 12), `preview` (0-2000) |
| `search_vault` | Free-text grep and/or glob search. Requires at least one of `grep`/`glob`. | `grep`, `glob`, `limit` (max 500) |
| `get_vault_record` | Read one record's frontmatter + body by exact vault-relative path. | `path` (e.g. `matter/acme.md`) |
| `create_vault_record` | Create a new record from `type` + `name` + optional `fields` (scaffold) or `content` (raw). | `type` (12 canonical), `name`, `content` or `fields` |
| `update_vault_record` | Patch under per-path mutex. Four orthogonal ops: `set`, `append`, `body_append`, `body_set`. | `path` + one or more ops |
| `promote_triage_to_task` | Convert a `triage/*` record into a `task/*` and mark the triage resolved. | `triagePath`, `matter?`, `owner?`, `priority?` |

`update_vault_record` writes to `matter/*` and `task/*` records trigger Plane forward-sync within 15 seconds *(packages/mcp-server/src/tools/alfred.ts:133)*. `set` is idempotent; `append` and `body_append` are not.

</Accordion>

|---|---|---|
| `spawn_alfred_task` | Hand a one-shot task to the principal's main Alfred agent via a Hermes main-profile cron job that fires once and self-destroys. | `task`, `channel?`, `to?`, `at_seconds?`, `name?`, `announce?` |
| `list_agents` | List the static agent catalogue: `main`, `learn-clerk`, `vault-curator`, `vault-janitor`, `vault-distiller`, plus surveyor config. | — |

`spawn_alfred_task` creates a cron job with `--at 1s --delete-after-run` *(packages/mcp-server/src/tools/alfred.ts:187)*. Set `announce: false` for silent background work that should not DM the principal. Not idempotent — calling twice schedules two runs.

<Accordion title="Temporal workflows (4 tools)">

Direct control over the tenant's Temporal server through `docker exec` into the temporal container *(packages/mcp-server/src/tools/alfred.ts:229)*.

| Tool | Purpose | Key params |
|---|---|---|
| `list_workflows` | List running + recently closed executions; optional visibility query. | `query?` (Temporal SQL-ish) |
| `describe_workflow` | Full detail for one execution — status, start/close, pending activities, last failure. | `wfId`, `run_id?` |
| `start_workflow` | Start a new execution by registered class name. | `workflow_type`, `task_queue`, `input?`, `workflow_id?` |
| `signal_workflow` | Send a Temporal signal to a running workflow. | `wfId`, `signal_name`, `input?`, `run_id?` |

Common workflow types on `alfred-learn`: `OnboardingPipelineWorkflow`, `BriefingWorkflow`, `EventProcessorWorkflow`, `ReflectionWorkflow`, `JudgmentWorkflow`, `TaskRunnerWorkflow` *(packages/mcp-server/src/tools/alfred.ts:261)*. `start_workflow` is idempotent only when paired with a stable `workflow_id` and Temporal's reuse-policy semantics on the worker side.

| Tool | Purpose | Key params |

| `get_decision` | Read one decision's full body and outcome record. | `id` |
| `list_pending_decisions` | Cards currently awaiting the principal — what is on `/desk` right now. | `include?` (pending/all), `limit?` |
| `list_state_changes` | Audit ledger of every `matter` / `task` mutation through state_mutator v2. | `target?`, `source?`, `since?`, `until?`, `limit?`, `offset?` |

`list_state_changes` is the canonical audit feed (`docs/STATE-MUTATION.md`). `source` values include `briefing.morning`, `steward`, `nightly_narrative`, `manual.<userid>`.

<Accordion title="Desk actions — act_on_decision, reverse_decision (2 tools)">

These two tools wrap the same `/api/v1/decisions` surface the `/desk` dashboard uses, so a connector can clear and unwind Desk cards on the principal's behalf *(packages/mcp-server/src/tools/alfred.ts:457-572)*.

| Tool | Purpose | Key params |
|---|---|---|
| `act_on_decision` | Act on one Desk card with the same five buttons the dashboard exposes (`delegate` / `defer` / `done` / `do` / `noise`). | `id`, `action`, `note?`, `source?`, `matter_ref?`, `task_ref?`, `source_headline?` |
| `reverse_decision` | Undo a decision back to pending — flips `state → reversed` and `DecisionRouterWorkflow` runs the inverse side-effects on the next tick. | `id` |

`act_on_decision` resolves to `POST /api/v1/decisions` *(packages/mcp-server/src/tools/alfred.ts:539-552)*. The action enum mirrors the dashboard exactly — `delegate` re-arms the source signal and lets the matched instinct's agent fire; `defer` parses a natural-language `note` into `resurface_at`; `done` resolves and seeds a learning observation; `do` (intent `take_mine` on the wire) spawns a `to_do/<ts>.md` for the principal; `noise` materialises a `signal_noise_pattern` so the next similar card is filtered upstream. The `note` field is **required for `delegate` and `defer`** (validated server-side via a `superRefine`) and optional for `done` / `do` / `noise`. `source` defaults to `needs_attention` (the common Desk case) but accepts `approval`, `judgment`, `to_do`, `desk_originated`, `pattern_proposal`, or `instinct_fire`. The id passed for a needs_attention card is the bare stem (e.g. `2026-05-28-04-15-xyz`) — the tool wraps it to `needs_attention/<id>.md` before POSTing. Not idempotent — each call writes a fresh decision record, and a retry against an already-handled card returns the new decision with the source already in its target state.

`reverse_decision` resolves to `POST /api/v1/decisions/:id/reverse` *(packages/mcp-server/src/tools/alfred.ts:568-571)*. Idempotent: a no-op on an already-reversed card returns `{ok: true, id, already_reversed: true}`. Best-effort by design — for `intent=delegate`, the source-record flip is reversible but a dispatched agent's outbound side-effects cannot be unwound, so ctrl-api stamps `delegate` decisions with `is_reversible: false` and the route returns HTTP 400 in that case. The four other intents (`defer`, `done`, `take_mine`, `noise`) reverse cleanly.

</Accordion>

|---|---|---|
| `get_openclaw_health` | Health envelope from the gateway — provider auth, queue depth, cron tick latency, MCP availability. | — |

<Accordion title="Tool dispositions and focused-subagent delegation (3 tools)">

The three tools that let Alfred himself manage the runtime-flippable DIRECT-or-DELEGATED disposition of every MCP server he loads — and reach delegated servers via an ephemeral focused subagent on the workers profile. See [Tool dispositions and delegation](/architecture/hermes-runtime#tool-dispositions-and-delegation) for the full architecture and [the linked skill](https://github.com/ssdavidai/alfred/blob/main/packages/mcp-server/skills/alfred-mcp-skill.md) at `packages/mcp-server/skills/alfred-mcp-skill.md` for the conversational playbook.

| Tool | Purpose | Key params |
|---|---|---|
| `list_tool_dispositions` | Read the live disposition map for the 9 MCP servers Hermes-main loads (`alfred`, `alfred-ctrl`, `sure`, `plane`, `vaultwarden`, `paperclip`, `execute`, `hass`, `files`). Cached ~60 s in-process; cheap to call at session start. | — |
| `set_tool_disposition` | Flip one server between `direct` (native tools in main's catalogue) and `delegated` (tools hidden on main; reachable via `delegate_to_focused_agent`). Triggers a debounced ~10 s Hermes restart. | `server`, `disposition`, `updated_by?` |
| `delegate_to_focused_agent` | Spawn a one-shot focused subagent on the workers profile with the same Alfred identity + journal. Returns plain text intended for verbatim relay. | `task`, `domain`, `context?` |

`list_tool_dispositions` resolves to [`GET /api/v1/agents/tool-disposition`](/api-reference/agents/get-tool-dispositions). Use at the top of a session to ground subsequent tool-vs-delegate choices — disposition can change between turns (Sir flips via dashboard or voice).

`set_tool_disposition` resolves to [`POST /api/v1/agents/tool-disposition`](/api-reference/agents/set-tool-disposition). Use when Sir says "demote X to delegated", "promote X to direct", "hide the sure tools", or when token-per-turn climbs and Alfred wants to suggest the flip himself. After the queued restart lands the new disposition is live; the canonical principal-facing line is *"I've queued the restart — give it about ten seconds."*

**Self-protection rule.** Three servers control Alfred's own self-management surface: `alfred-ctrl` (admin/agents/state/health), `alfred` (vault + decisions + briefings + this very disposition surface), and `execute` (the Composio gateway). The backend accepts the flip — a deliberate rescue is always possible — but the MCP tool's prompt instructs Alfred never to flip any of the three without Sir's verbatim confirmation phrase *"yes, change my Alfred's tool disposition"* in his most recent message. Same pattern as the HA self-destruct guard.

`delegate_to_focused_agent` resolves to [`POST /api/v1/agents/focused-subagent`](/api-reference/agents/spawn-focused-subagent). Two trigger conditions: (1) the target server is currently `delegated` in `list_tool_dispositions` so the LLM has no native tools from it this turn; (2) the work is a tool-heavy fanout — Gmail batch, calendar across multiple calendars, Paperclip multi-issue update, Sure transaction triage — and inlining 10–20 calls would blow the context budget. **Relay the subagent's reply verbatim**; the subagent's wording is calibrated for direct relay, and rewriting it dilutes correctness and burns tokens. 60 s timeout. Not idempotent — each call spawns a fresh session keyed `focus-<domain>-<short-hash>`.

</Accordion>

<Accordion title="Device pairing approval (1 tool)">

| Tool | Purpose | Key params |
|---|---|---|
| `approve_device` | Approve a pending Hermes DM-pairing code for Telegram, Slack, Discord, WhatsApp, or Signal. | `platform`, `code` (8-char) |

When an unknown messaging account DMs Alfred's gateway, Hermes hands it a one-hour pairing code that needs operator approval. The dashboard's `/dashboard/devices` page lists pending codes; this tool drives the approval programmatically. Revoke and clear-pending are not exposed — those can lock the principal's channels out and should not be driven by a remote LLM *(packages/mcp-server/src/tools/alfred.ts:333)*.

</Accordion>

<Accordion title="Notifications (1 tool)">

| Tool | Purpose | Key params |
|---|---|---|
| `notify_principal` | Send a message to the principal on their preferred channel (Telegram, Slack). | `message`, `channel?` (auto/telegram/slack), `urgency?`, `to?` |

<Warning>
`notify_principal` is the right tool for any "ping the principal" flow — never `composio_execute`. Telegram is not a Composio toolkit; it is a Hermes main-profile channel and only the main runtime can reach it. ctrl-api creates a one-shot Hermes main-profile cron job that delivers the message and returns `delivered: true` only once the channel send is confirmed *(packages/mcp-server/src/tools/alfred.ts:511-515)*.
</Warning>
