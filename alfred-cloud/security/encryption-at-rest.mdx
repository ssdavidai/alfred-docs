<Note>
Every byte that matters lives on `/mnt/encrypted`. Nothing of consequence — vault, streams, Hermes config, Temporal DB, Vaultwarden — sits on the unencrypted root filesystem.
</Note>

## What we encrypt

The data volume on every tenant is encrypted with **LUKS2** (Linux Unified Key Setup, version 2) using **AES-256-XTS**. The passphrase is generated per-instance at provisioning time and never reused. The Hetzner Cloud volume is attached, formatted with LUKS2, then mounted as `/mnt/encrypted` — every directory below is on that one encrypted volume. *(`packages/ctrl/src/templates/cloud-init.yaml.njk`)*

| Path | What it holds |
|---|---|
| `/mnt/encrypted/vault` | The principal's Markdown vault. Bind-mounted into every container that needs it. |
| `/mnt/encrypted/alfred` | Tenant secrets file (`.gateway-token`), authorised phone numbers, onboarding state, Composio user id, stream JSONLs. |
| `/mnt/encrypted/alfred/.agentmail-credentials.json` | The inbox-scoped AgentMail key. |
| `/mnt/encrypted/alfred/.composio-user-id` | Composio user id fallback when env-injection failed. *(`packages/ctrl/src/api/routes/integrations.ts:123`)* |
| `/mnt/encrypted/alfred/.authorized-phone-numbers.json` | Allowlist for inbound SMS / voice. |
| `/mnt/encrypted/alfred/streams` | Stream events and configs (the raw inbound event log). |
| `/mnt/encrypted/hermes` | Hermes runtime config + per-profile state. |
| `/mnt/encrypted/hermes/profiles/main` | Main agent profile — config.yaml, .env, SOUL.md, SessionStore, plugins. |
| `/mnt/encrypted/hermes/profiles/workers` | Workers profile (clerk + ephemeral runs). |
| `/mnt/encrypted/hermes/profiles/heavy` | Heavy-reasoning profile (Opus-class). |
| `/mnt/encrypted/temporal` | Temporal SQLite database (workflow state). |
| `/mnt/encrypted/ollama` | Cached embedding model weights for the surveyor (`nomic-embed-text`). |
| `/mnt/encrypted/vaultwarden` | Per-tenant Vaultwarden SQLite + attachments — every secret currently in `.env` plus future credentials. |
| `/mnt/encrypted/mcp-server` | Per-tenant MCP HTTP server data (Claude Custom Connector OAuth state). |
| `/mnt/encrypted/vault/.auth/authorized_senders.json` | Allowlist for inbound email senders. |
| `/mnt/encrypted/plane` | Plane PM stack volumes (`pgdata/`, `redis/`, `rabbitmq/`, `uploads/`) — when `plane_enabled` is on. |
| `/mnt/encrypted/sure` | Sure personal-finance stack volumes (`pgdata/`, `redis/`) — when `sure_enabled` is on. |

The `/mnt/encrypted/{plane,sure,mcp-server,vaultwarden}` directories are created **unconditionally** at provision time. The cost of an empty directory is zero, and creating them lazily would mean flipping a sidecar feature flag (e.g. `sure_enabled`) would also need re-running cloud-init before the corresponding stack could start.

At rest, the volume content is **unreadable without the LUKS passphrase**. Even Hetzner staff with physical access to the disk see only ciphertext.

## The encryption parameters

| Parameter | Value |
|---|---|
| Container format | LUKS2 (header v2.0) |
| Cipher | `aes-xts-plain64` |
| Key size | 512 bits (XTS uses two 256-bit halves) |
| Hash | `sha256` |
| PBKDF | `argon2id` (LUKS2 default; memory-hard, GPU-resistant) |
| Sector size | 4096 |

XTS is the standard AES mode for storage-at-rest — it provides confidentiality without authentication, which is acceptable here because tampering with ciphertext is constrained at higher layers (we don't trust the disk to provide integrity, but the file content is signed by the writers — vault commits are Markdown text the principal can re-verify, SQLite has a WAL checksum, etc.).

## The passphrase lifecycle

This is the trickiest part to get right, and the part most cloud LUKS deployments get wrong. **The passphrase is never written anywhere a Hetzner metadata API could see it.**

<Steps>
 <Step title="Generated post-boot via SSH">
 Cloud-init formats the disk with LUKS2 but uses a **temporary** keyfile. After cloud-init finishes, the provisioner SSHs into the box, generates the per-instance passphrase, adds it as a LUKS keyslot, then removes the temporary keyfile.

 Why this and not cloud-init `user_data`? Because Hetzner's metadata API at `169.254.169.254` is readable by anything on the VM — any compromised container could read its own `user_data` block. Putting the passphrase there would leak it on first compromise.
 </Step>
 <Step title="Stored on disk only at `/opt/alfred/luks.key`">
 The keyfile lives at `/opt/alfred/luks.key` on the host — readable only by root (`chmod 0400`), used by the `alfred-luks.service` systemd unit to auto-unlock the volume on boot.

 The host's root filesystem is **not** encrypted (it's a stock Hetzner image with the bootloader and kernel). Compromising root on the host trivially reads this keyfile — encryption-at-rest protects against disk-level theft, not against root compromise of a running tenant. See [Network model](/alfred-cloud/security/network-model) for what reduces the chance of root compromise (hardened SSH, fail2ban, UFW, no public service ports).
 </Step>
 <Step title="Held in memory by systemd for the volume's lifetime">
 Once the volume is unlocked at boot, the LUKS master key lives in the kernel's keyring. Userspace processes never see the passphrase again — they just read and write through the mounted `/mnt/encrypted` filesystem like any other ext4 mount.
 </Step>
 <Step title="Backed up to operator-side storage">
 The keyfile is downloaded into `data/ssh_keys/<instance-id>/luks.key` on the operator's machine at provision time.

 This is the **disaster-recovery escape hatch** — if Hetzner loses the disk, the operator can re-mount the encrypted volume from its raw bytes plus this backed-up keyfile.
 </Step>
</Steps>

## Defence in depth

Encryption at rest is one layer. The full chain is:

| Layer | What it defends against |
|---|---|
| LUKS2 on `/mnt/encrypted` | Disk theft, raw-disk forensics by hosting-provider staff |
| Container `cap_drop: ALL` + `no-new-privileges: true` | Container escape into the host root filesystem *(`docker-compose.yaml:211,310`)* |
| `127.0.0.1` bindings on every Alfred port | Network-level disk-content exfiltration (you'd have to be on the box) |
| Per-tenant Vaultwarden master password (AES-256 on top of LUKS) | A compromised LUKS keyfile still doesn't reveal Vaultwarden contents |
| Tenant `.env` placed on `/mnt/encrypted` only after the host is provisioned | A pre-boot disk image grab gets you nothing useful |

The Vaultwarden layering is the most security-meaningful: even if an attacker obtained the LUKS master key, the Bitwarden-compatible vault on top still requires the principal's master password (PBKDF2-derived) to decrypt individual records. See [Per-tenant isolation → Vaultwarden](/alfred-cloud/security/per-tenant-isolation#vaultwarden).

<Warning>
LUKS protects data **at rest**. While the tenant is running, `/mnt/encrypted` is mounted and readable to root and to container processes that have it bind-mounted. Encryption at rest is one layer among many — see [Agent sandboxing](/alfred-cloud/security/agent-sandboxing) for what limits in-flight access.
</Warning>
