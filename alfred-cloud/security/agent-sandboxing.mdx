<Note>
Hermes agents are powerful — they can read your vault, send email, make calls, move money. The seven layers below are what keeps the blast radius bounded when a model makes a mistake or a prompt-injection lands.
</Note>

## What an agent is, in this system

Alfred runs on the **Hermes Agent runtime** — one Docker image, three supervised profiles:

- **`main`** (port `:18789`) — user-facing chat. Memory and channels enabled.
- **`workers`** (port `:18790`) — background subagents (clerk, curator, janitor, distiller, ephemeral runs). Concurrency-capped.
- **`heavy`** (port `:18791`) — Opus-class reasoning for onboarding and Reflection.

Every profile speaks the OpenAI Responses API natively (`POST /v1/responses`, `POST /v1/runs`) authenticated by the gateway token (`HERMES_API_SERVER_KEY`). Each profile registers the same **six MCP servers** in its `config.yaml`. *(`packages/hermes/docker/supervisor.sh:7–9`)*

## The seven layers

### 1. The gateway tool allowlist

Each Hermes profile's `config.yaml` declares **`gateway.tools.allow`** explicitly. The MCP servers a profile registers (`alfred-ctrl`, `alfred`, `sure`, `plane`, `vaultwarden`, `execute`) are configured per-profile. *(`packages/hermes/hermes-config.yaml.njk`)*

- Nothing is implicit. A new MCP tool is invisible to the agent until it's added to the config and Hermes is reloaded.
- The `workers` profile registers a deliberately narrower set than `main` (no chat-channel MCP).
- The `heavy` profile inherits `workers`' surface (reasoning + reflection, not interactive channels).

### 2. MCP `self` is one endpoint, not 41 prefixed tools

The agent's primary `ctrl-api` access is **one MCP tool** (`alfred-ctrl`, an HTTP MCP wrapper of `ctrl-api` at `:3100`), not 41 separately-named tools. The endpoint catalogue is documented in the workspace `TOOLS.md`. *(`packages/hermes/workspace-template/docs/TOOLS.md`)*

Why this matters:

- The agent can only hit endpoints `ctrl-api` exposes — `ctrl-api` is the policy gate. If a route is not implemented, the agent cannot reach it.
- `ctrl-api` cannot reach beyond the tenant (no outbound HTTP except through Composio's gateway and the LLM provider).
- Adding a new capability means adding a `ctrl-api` route, which goes through code review and the promotion-contract enforcement.

### 3. The Composio gateway for third-party access

Every third-party action (read Gmail, send Slack, create Notion page, charge Stripe) goes through the **`execute` MCP server**, which proxies into Composio with the tenant's `COMPOSIO_USER_ID`. *(`packages/ctrl/src/api/routes/integrations.ts:3098`)*

- Composio holds the OAuth tokens server-side.
- The tenant only holds connection IDs — never the underlying access/refresh tokens.
- Every connection lookup re-verifies ownership (see [Per-tenant isolation → Composio](/alfred-cloud/security/per-tenant-isolation#composio)).

An agent that's tricked into "go read this user's Notion" cannot escape the tenant boundary — `user_id` is enforced server-side and re-checked locally.

### 4. Ephemeral subagents with scoped tools

The TaskRunner (and the `workers` profile in general) spawns short-lived agents per task with **scoped tool access**:

- A subagent tasked with "summarise this Slack thread" gets only the Slack tools, not the email or Notion tools.
- A subagent tasked with "post a payment-failure note to Plane" gets only the Plane tools.
- Subagent lifecycle is bounded — `workers` profile concurrency is capped to prevent runaway spawning.

This means a prompt injection that lands in a Slack message body cannot use the resulting subagent to read your email, because the email tools aren't in the subagent's surface in the first place.

### 5. The workspace shell is scoped to a directory

The Hermes workspace exposes `bash`, `read`, `write`, `edit`, `find`, and friends — but they're scoped to a workspace directory inside the Hermes container, not the host root filesystem.

- The agent cannot `cat /etc/passwd`. The shell tool refuses to leave the workspace root.
- The workspace is at `/home/node/.hermes/workspace/` inside the container — itself inside an unprivileged Docker container with `cap_drop: ALL` and `no-new-privileges: true`. *(`docker-compose.yaml:310–311`)*
- The vault is bind-mounted into the container at a specific path; the agent's vault reads/writes go through `ctrl-api` (which enforces the promotion contract), not raw filesystem operations.

### 6. The self-restart guardrail

Restarting `hermes` or `ctrl-api` from inside the agent requires an `X-Confirm-Self-Restart: yes` header. *(`packages/ctrl/src/api/routes/admin.ts:299–302`)*

```ts
const confirmHeader = req.headers["x-confirm-self-restart"];
// Refuses without the header — prevents the agent from accidentally
// killing its own session.
```

Without the header, the route returns an error: "Refusing to restart `<service>` without X-Confirm-Self-Restart:yes header — this kills the running session or API connection". *(`packages/ctrl/src/api/routes/admin.ts:302`)*

The same guard applies to `/api/v1/admin/credentials` mutations that affect the running container. *(`packages/ctrl/src/api/routes/credentials.ts:343`)*

### 7. Confirm-before-destruct on destructive operations

The workspace skills explicitly require the principal's confirmation before:

- **Delete** operations on vault records, tasks, matters, instincts.
- **Terminate** operations on long-running workflows / chores.
- **Cancel** operations on scheduled actions.
- **Live-chore-trigger** — running a chore outside its schedule.

The destructive-ops policy lives in the `alfred-destructive-ops` skill (`packages/hermes/workspace-template/skills/alfred-destructive-ops/SKILL.md`), which is loaded by every relevant Hermes profile and instructs the model to surface a confirmation prompt.

This is the most "social" layer — it depends on the model following the skill. The other six layers above are enforced in code regardless of model behaviour.

## The layered defence model

The seven layers stack. To exfiltrate one vault record to an attacker-controlled URL via a prompt-injected message, an attacker would need to bypass:

1. The gateway allowlist (HTTP egress beyond Composio is not in the agent's tool set)
2. MCP `self` (`ctrl-api` doesn't expose a generic-HTTP-fetch endpoint)
3. The Composio gateway (Composio's APIs are app-specific, not arbitrary HTTP)
4. Subagent tool scoping (a subagent spawned by a poisoned message has a narrower surface)
5. The workspace shell scope (no `curl http://attacker.example`)
6. The self-restart guardrail (no way to disable any of the above)
7. Confirm-before-destruct (irrelevant for read exfil, but blocks the "delete-after" cover-up)

A single layer failing is not catastrophic. **No single tool in the surface lets the agent hit an arbitrary URL with arbitrary content.** That property is the whole point of the layered model.

## What the layers do NOT prevent

Honest scope of what's still possible:

- **The agent can send email to attacker.example via the Gmail MCP.** Gmail is in the allowlist; the email tool is by-design. Mitigation: the per-instinct discretion gate (the agent doesn't send the email autonomously unless the instinct is at "Acting" tier with high confidence) — see [Agent autonomy](/configuration/mode-flags).
- **The agent can write a vault record summarising secrets the principal pasted.** Mitigation: vault writes are visible in the activity log and the `system-hermes-sessions` stream.
- **The agent can run a chore that calls Composio with attacker-supplied parameters.** Mitigation: chore code is principal-authored Markdown + Python; the agent doesn't write chores autonomously.
- **The agent can hallucinate a wrong tool call.** Mitigation: idempotency keys on side-effectful routes; confirm-before-destruct on destructive ones.

The system is a **trust-but-audit** model on top of a **trust-but-scope** tool surface. The agent can do useful work; the audit trail catches everything it did; the scopes mean it can't do most catastrophic things even if it tried.
