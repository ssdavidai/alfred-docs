<Note>
Backups happen once a day, encrypted twice (LUKS volume + restic password), and are retained on the long tail for six months. The LUKS keyfile is backed up at provision time and never touched again — it's the recovery escape hatch if Hetzner ever loses the disk.
</Note>

## The daily backup

A daily `restic` job runs at **03:00 host-local** via the `alfred-backup.timer` systemd unit installed by cloud-init.

<Steps>
 <Step title="Quiesce the writers">
 The job stops three containers that hold open SQLite write handles or in-flight workflow state:
 - **`alfred`** — the vault specialists daemon (Curator, Janitor, Distiller, Surveyor)
 - **`hermes`** — the runtime container (all three profiles share one container)
 - **`temporal`** — the workflow engine

 Quiescing avoids SQLite write-mid-snapshot inconsistency (WAL-checkpoint races) and prevents Temporal from running a workflow tick that mutates state between snapshot of one file and the next.
 </Step>
 <Step title="Snapshot `/mnt/encrypted`">
 `restic backup /mnt/encrypted --exclude=/mnt/encrypted/temporal` runs the actual snapshot.

 Temporal state is excluded because (a) it's recoverable — workflows resume from their last completed step — and (b) it churns rapidly and would bloat the dedup index.

 Restic deduplicates blocks against the previous snapshot, so the day-over-day cost is small.
 </Step>
 <Step title="Restart the writers">
 The three stopped containers restart. Quiesce window is typically **30–90 seconds**.
 </Step>
 <Step title="Prune to retention policy">
 `restic forget --keep-daily 7 --keep-weekly 4 --keep-monthly 6 --prune` enforces retention. Older snapshots have their blocks released and the repository is compacted.
 </Step>
</Steps>

## Retention

| Keep | Window |
|---|---|
| **7 daily** | The last seven days of snapshots |
| **4 weekly** | The latest snapshot in each of the last four ISO weeks |
| **6 monthly** | The latest snapshot in each of the last six calendar months |

Worst-case recovery point: **24 hours** (if the daily ran successfully). After 6 months, the snapshot is gone permanently from restic.

## Where backups live

**Destination**: Hetzner Object Storage (S3-compatible), EU region — same residency as the tenant.

**Encryption**: restic encrypts every block client-side with a per-tenant restic password (AES-256-CTR + Poly1305). Hetzner Object Storage sees only opaque ciphertext.

**Restic password storage**:

| Location | Who can read | Notes |
|---|---|---|
| `/opt/alfred/restic.env` on the tenant | root on the tenant | Used by the systemd backup unit |
| `data/ssh_keys/<instance-id>/restic.env` on the operator machine | operator | The recovery escape hatch if the tenant is unrecoverable |

The restic password is **never** stored at the SaaS host, never at Hetzner, and never in any centralised key vault. Operator + tenant are the only two locations.

## What is and is not in the snapshot

| Path | Included? | Why |
|---|---|---|
| `/mnt/encrypted/vault` | Yes | Principal's vault — irreplaceable |
| `/mnt/encrypted/alfred` | Yes | Tenant state (settings.json, gateway token, streams) |
| `/mnt/encrypted/hermes` | Yes | Hermes profile state — SessionStore, SOUL.md, memories |
| `/mnt/encrypted/vaultwarden` | Yes | Vaultwarden DB + attachments |
| `/mnt/encrypted/ollama` | Yes | Embedding model cache — re-downloadable but slow |
| `/mnt/encrypted/mcp-server` | Yes | Claude Custom Connector OAuth state |
| `/mnt/encrypted/plane`, `sure`, `vexa` | Yes (when enabled) | Sidecar Postgres / Redis / MinIO data |
| `/mnt/encrypted/temporal` | **No** | Excluded — workflows resume from last completed step |
| `/opt/alfred/luks.key` | **No** | Backed up separately at provision time (see below) |
| `/var/lib/docker` | No | Images are re-pullable from the registry |
| Host root filesystem | No | Stock Hetzner image |

## The LUKS keyfile backup

The LUKS passphrase is the **other** thing you need to recover. It's backed up **once**, at provision time, to the operator's machine at `data/ssh_keys/<instance-id>/luks.key`.

This is deliberate: the keyfile doesn't change over the lifetime of the volume, so re-backing it up daily would add risk without benefit. One backup, one copy, one location.

**Why this matters**: even if Hetzner loses the disk entirely, the operator can:

1. Provision a fresh Hetzner volume.
2. `restic restore` the latest snapshot from Hetzner Object Storage (the restic password is on the operator's machine).
3. `cryptsetup luksOpen` the snapshot's `/mnt/encrypted` image with the backed-up keyfile.
4. Mount, verify, and re-attach to a fresh tenant VM.

Without the keyfile, the restored snapshot is a wall of ciphertext.

## Recovery procedure

The operator-side restore workflow, abbreviated:

<Tabs>
 <Tab title="Same-VM restore (lost a file)">
 ```bash
 # Operator SSHs in, restic is configured
 restic snapshots
 restic mount /mnt/restore
 cp /mnt/restore/snapshots/latest/mnt/encrypted/vault/<path> \
 /mnt/encrypted/vault/<path>
 umount /mnt/restore
 ```
 Quiesce is not required for individual-file restore as long as the path being restored isn't being written.
 </Tab>
 <Tab title="Same-VM full restore (corruption)">
 ```bash
 # 1. Stop the stack
 docker compose down

 # 2. Wipe /mnt/encrypted (the LUKS volume remains, just empty it)
 rm -rf /mnt/encrypted/*

 # 3. Restore
 restic restore latest --target /mnt/encrypted

 # 4. Bring it back up
 docker compose up -d
 ```
 </Tab>
 <Tab title="New-VM restore (Hetzner lost the disk)">
 ```bash
 # On the operator's machine
 # 1. Provision a fresh VM + volume (operator CLI)
 alfred-ctrl instance create --slug <same-slug> --restore-from <old-id>

 # 2. SSH in, mount the empty LUKS volume with the backed-up keyfile
 scp data/ssh_keys/<old-id>/luks.key root@<new-ip>:/opt/alfred/luks.key
 ssh root@<new-ip> 'systemctl start alfred-luks.service'

 # 3. Restore restic snapshot
 ssh root@<new-ip> 'RESTIC_PASSWORD_FILE=/opt/alfred/restic.env \
 restic -r s3:... restore latest --target /mnt/encrypted'

 # 4. Bring stack up
 ssh root@<new-ip> 'cd /opt/alfred && docker compose up -d'
 ```
 The new tenant gets a new Hetzner IP. Tailscale re-handshakes automatically; Cloudflare DNS is updated by the operator CLI as part of the create step.
 </Tab>
</Tabs>

End-to-end new-VM restore from a same-day snapshot is **roughly 15–25 minutes**, dominated by the restic download from Hetzner Object Storage. The longer pole on a fresh VM (no golden snapshot) is the LLM image pull plus the Ollama embedding model download — both happen in parallel with the restore.

## What backups do NOT cover

| Failure mode | Covered by backups? | Mitigation |
|---|---|---|
| Hetzner loses the disk | Yes | Daily restic + LUKS keyfile backup |
| Bug deletes a vault record | Yes | Restore from yesterday's snapshot |
| Principal accidentally deletes a vault file | Yes | Same |
| Ransomware encrypts `/mnt/encrypted` | Yes | Same — but see Warning below |
| Operator loses both the restic password and the LUKS keyfile | **No** | Keep operator-side backups of `data/ssh_keys/<id>/` |
| Hetzner Object Storage region outage | Partial | Restore would be deferred until region recovers; consider an off-site copy for critical use |
| Subscription cancelled, 30 days elapsed | **N/A** | Backups are deleted by design — see [Data residency](/alfred-cloud/security/data-residency) |

<Warning>
**Backups are encrypted with a password held on the operator's machine.** That machine's security posture matters. The operator should hold the restic password (and the LUKS keyfile collection) inside a hardware-backed secret store (1Password with biometric unlock, a YubiKey-secured pass repo, or equivalent) — not in plaintext on a laptop disk.
</Warning>

## Verification

Restoring is the only way to know a backup is good. The operator-side runbook includes a quarterly **restore-rehearsal** on a fresh VM — restore the latest snapshot, bring the stack up, run a smoke test, destroy the rehearsal VM. The rehearsal is intentionally manual; an automated rehearsal that always passes is no rehearsal at all.
