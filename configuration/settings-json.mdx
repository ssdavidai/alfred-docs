title: "settings.json"

---

`/alfred-data/settings.json` is the runtime knob shared between the dashboard, `ctrl-api`, and `alfred-learn`. It holds principal-chosen overrides for behaviour you don't want baked into the compose file — most notably the three [mode flags](/configuration/mode-flags).

The file lives on the shared `alfred_data` Docker volume *(`docker-compose.yaml:1494`)*, mounted at `/alfred-data` in every container that needs to read or write it.

---

## Who writes, who reads

<Note>
`ctrl-api` is the **only** writer. `alfred-learn` and other consumers read the file directly but never patch it. This avoids the multi-process write contention that bit earlier builds.
</Note>

- **Writer:** `ctrl-api` *(`packages/ctrl/src/api/routes/settings.ts`)*. Every write goes through one of the endpoints below; there is no other code path that touches the file.
- **Readers:** `alfred-learn` activities for the three mode flags *(`packages/learn/src/activities/state_mutator.py:251-276`, `signal_actions.py:160-180`, `task_creation.py:185-208`)*. The dashboard reads via `ctrl-api`'s `GET` endpoints.

---

## Atomic write strategy

The writer never writes the file in place. It uses the standard temp-file + rename trick *(`settings.ts:126-133`)*:

<Steps>
  <Step title="Read">
    Read the existing `settings.json` (or `{}` if it doesn't exist yet).
  </Step>
  <Step title="Modify">
    Set the new key/value in the in-memory object.
  </Step>
  <Step title="Write temp">
    Write the full JSON to `/alfred-data/settings.json.tmp`.
  </Step>
  <Step title="Rename">
    `rename(2)` `.tmp` → `settings.json`. On POSIX this is atomic — no reader can ever observe a partial write.
  </Step>
</Steps>

Because there is exactly one writer process, the read-modify-write cycle can't race with itself. A reader that opens the file mid-rename always gets either the pre-rename or post-rename version, never a torn middle.

## Schema

The current registry of supported keys is fixed in code *(`settings.ts:56-72`)*:

| Key | Type | Resolved by |
|-----|------|-------------|
| `signal_action_mode` | `"live"` \| `"shadow"` \| `"live_high_confidence_only"` | `signal_actions._resolve_signal_action_mode` |
| `state_mutator_mode` | `"live"` \| `"shadow"` \| `"live_high_confidence_only"` | `state_mutator._resolve_state_mutator_mode` |
| `auto_task_create_mode` | `"live"` \| `"shadow"` \| `"live_high_confidence_only"` | `task_creation._resolve_auto_task_create_mode` |

A typical live file looks like:

```json
{
  "signal_action_mode": "live",
  "state_mutator_mode": "shadow",
  "auto_task_create_mode": "live"
}
```

Unknown keys are tolerated (writers reject them; readers ignore them) so adding a new flag is a forward-compatible change.

## HTTP endpoints

The `ctrl-api` server exposes three routes *(`settings.ts`)*:

| Method | Path | Body | Returns |
|--------|------|------|---------|
| `GET` | `/api/v1/settings` | — | All flags with `{ mode, source, env_override_active }` per key |
| `GET` | `/api/v1/settings/:key` | — | Single-flag resolution (same envelope) |
| `PUT` | `/api/v1/settings/:key` | `{ "mode": "live" \| "shadow" \| "live_high_confidence_only" }` | New resolved value |

A legacy hyphenated alias `/api/v1/settings/signal-action-mode` is kept for backwards compatibility with older dashboard builds *(`settings.ts:353`)*.

<CodeGroup>

```bash curl
curl -X PUT https://api.${DOMAIN}/api/v1/settings/signal_action_mode \
  -H "Authorization: Bearer ${AAS_API_KEY}" \
  -H "Content-Type: application/json" \
  -d '{"mode": "shadow"}'
```

```javascript JavaScript
await fetch(`https://api.${DOMAIN}/api/v1/settings/signal_action_mode`, {
  method: "PUT",
  headers: {
    "Authorization": `Bearer ${AAS_API_KEY}`,
    "Content-Type": "application/json",
  },
  body: JSON.stringify({ mode: "shadow" }),
});
```

</CodeGroup>

## Editing the file by hand

Editing `/alfred-data/settings.json` directly works — the next read on either side picks up the change — but it's not recommended because:

1. You lose the atomic write (a partial save can be observed by a reader).
2. You bypass the validator and can write any string into the file. The resolvers will log a warning and fall back to the default, but you lose the dashboard's ability to display the current mode.

If you must edit by hand (e.g. emergency recovery), shell into a container that mounts the volume:

```bash
docker compose exec ctrl-api sh -c 'cat /alfred-data/settings.json'
docker compose exec ctrl-api sh -c 'cat > /alfred-data/settings.json' < my-new-settings.json
```

A dedicated env var override is almost always the safer alternative — see [mode flags resolution](/configuration/mode-flags#resolution-precedence).
