Alfred ships its tool catalogue as six MCP apps reachable over HTTP at `mcp.{$DOMAIN}` *(packages/mcp-server/src/index.ts:96–106, 244–334)*. Any MCP client — claude.ai (browser), Claude Desktop, Claude Code — can connect to those apps and start using the ~157 tools that drive the vault, the sidecars, and Composio.

This page covers wiring up each client. The dashboard does most of the work for you at `/settings#agent` — it lists every MCP URL, lets you reveal-once-and-rotate the approval secret, and offers one-click downloads of the skill bundles each app needs.

## The HTTP MCP server

The `mcp-server` container *(docker-compose.yaml:623–640)* listens on port **8787** and is reverse-proxied by Caddy from `mcp.{$DOMAIN}` *(caddy/Caddyfile)*. Each of the six MCP apps is mounted at its own path *(packages/mcp-server/src/index.ts:299–334)*:

```
POST https://mcp.{$DOMAIN}/alfred/mcp
POST https://mcp.{$DOMAIN}/sure/mcp
POST https://mcp.{$DOMAIN}/plane/mcp
POST https://mcp.{$DOMAIN}/vaultwarden/mcp
POST https://mcp.{$DOMAIN}/execute/mcp
POST https://mcp.{$DOMAIN}/hermes/mcp
```

OAuth metadata for each app is served at `/.well-known/oauth-protected-resource/<app>/mcp` *(packages/mcp-server/src/index.ts:96–106)*, and the standard OAuth routes (`/authorize`, `/token`, `/register`, `/revoke`) are mounted at the apex *(line 110–117)*.

## The MCP_APPROVAL_SECRET handshake

Alfred uses one pre-shared secret per tenant for the MCP authorisation flow: **`MCP_APPROVAL_SECRET`** *(packages/mcp-server/src/env.ts:12)*, generated by `bootstrap.sh` and stored in `.env`. The dashboard surfaces it (reveal-once) on `/settings#agent` and offers in-place rotation.

There are **two authentication paths** *(packages/mcp-server/src/index.ts:210–242)*:

### Path A — Browser OAuth (claude.ai)

1. claude.ai POSTs to `/alfred/mcp` with no auth.
2. The server returns `401` with a `WWW-Authenticate` header pointing at the per-app metadata.
3. claude.ai follows the OAuth flow: `/register` → `/authorize` (HTML form).
4. The form asks for the **approval secret**. The principal pastes it; the server timing-safe-compares to `MCP_APPROVAL_SECRET`.
5. On match, the server issues an auth code → token; claude.ai stores the token for the connection. The token is valid for **one hour** *(packages/mcp-server/src/oauth/provider.ts:35, `ACCESS_TOKEN_TTL_MS`)*.

### Path B — Bearer bypass (Claude Desktop, Claude Code, scripts)

For clients that don't need a browser round-trip, paste the approval secret directly as the bearer token:

```
Authorization: Bearer <MCP_APPROVAL_SECRET>
```

The server timing-safe-compares the bearer to the approval secret *(packages/mcp-server/src/index.ts:222)* and short-circuits the full OAuth verifier, synthesising the `auth.extra` shape the tool dispatcher expects. Blast radius is the same as a fully OAuth'd token — the secret can already mint one via `/approve` — but this path removes the round-trip and works in headless contexts.

## Wiring it into each client

<Tabs>
  <Tab title="claude.ai (browser)">
    1. Open claude.ai, then **Settings → Connectors → Add custom connector**.
    2. Paste each MCP URL one by one (e.g. `https://mcp.{your-domain}/alfred/mcp`). Give each a name (`Alfred`, `Sure`, `Plane`, `Vaultwarden`, `Execute`, `Hermes`).
    3. Click **Connect** on the new connector. Browser opens the OAuth form.
    4. Paste the **approval secret** from `/settings#agent` into the form. Submit.
    5. The connector lands as `Connected`; the tools appear in the model's catalogue.

    Repeat per app — claude.ai treats each `<app>/mcp` URL as a distinct connector.
  </Tab>

  <Tab title="Claude Code">
    Add the servers via the CLI (one command per app):

    ```sh
    claude mcp add --transport http alfred https://mcp.your-domain.com/alfred/mcp \
      --header "Authorization: Bearer YOUR_MCP_APPROVAL_SECRET"

    claude mcp add --transport http alfred-sure https://mcp.your-domain.com/sure/mcp \
      --header "Authorization: Bearer YOUR_MCP_APPROVAL_SECRET"

    claude mcp add --transport http alfred-plane https://mcp.your-domain.com/plane/mcp \
      --header "Authorization: Bearer YOUR_MCP_APPROVAL_SECRET"

    claude mcp add --transport http alfred-vaultwarden https://mcp.your-domain.com/vaultwarden/mcp \
      --header "Authorization: Bearer YOUR_MCP_APPROVAL_SECRET"

    claude mcp add --transport http alfred-execute https://mcp.your-domain.com/execute/mcp \
    ```

    Then `claude mcp list` to verify. Each server's tools become callable as `mcp__alfred__*`, `mcp__alfred-sure__*`, and so on.

    For project-scoped wiring instead of user-scoped, add `--scope project` and check the resulting `.mcp.json` into the repo (omitting the secret — use an env-var substitution).

## Picking which apps to connect

You don't have to connect all six. A common minimal setup:

- **`alfred`** — vault read/write, agent delegation, workflow orchestration. The general-purpose surface.
- **`execute`** — Composio. Connect this and you get Gmail / GitHub / Notion / Slack / Calendar / Drive in one shot.

Add **`sure`** if you actually use the personal-finance sidecar; **`vaultwarden`** if you want credential management from chat; **`plane`** if your projects live there; **`hermes`** if you want claude.ai to schedule recurring prompts or delegate long-form work to the Alfred runtime.

## Rotating the secret

If you suspect the approval secret has leaked, rotate it from `/settings#agent` *(ctrl-api: packages/ctrl/src/api/routes/claudeSetup.ts, the rotate handler)*. Rotation:

1. Generates a new 64-char hex value.
2. Surfaces it **exactly once** in the response.
3. Patches `.env` (`MCP_APPROVAL_SECRET` + `MCP_APPROVAL_SECRET_ROTATED_AT`).
4. Restarts `mcp-server` so the new value takes effect.

All existing connector tokens become invalid; reconnect each client with the new secret. There is no key rotation grace period — the old value is replaced atomically.

<Note>
The `mcp-server` container is per-tenant. On the single-VM stack you have exactly one — the same six MCP URLs apply to every client you wire up. Per-client scoping is achieved via the OAuth flow's per-app token binding *(packages/mcp-server/src/index.ts:265–276)*, which prevents a token bound to `sure` from calling `vaultwarden` tools.
</Note>
