title: "Vaultwarden"
description: "Self-hosted credentials, with a deliberately narrow MCP surface."

[Vaultwarden](https://github.com/dani-garcia/vaultwarden) is the Bitwarden-compatible password manager Alfred ships as its credentials sidecar. The UI lives at `vault.{$DOMAIN}` *(caddy/Caddyfile)*; secrets sit in `vaultwarden_data` *(docker-compose.yaml:278)*; the MCP surface lives in the `vaultwarden` app with **14 tools** *(packages/mcp-server/src/tools/vaultwarden.ts:31–240)*.

## The three containers

| Service | Image | Purpose |
|---|---|---|
| `vaultwarden` | `vaultwarden/server:latest` | The actual Bitwarden-compatible server on `:80` |
| `vault-signup` | `ssdavidai00/alfred-vault-init:latest` | One-shot: registers the owner account using `OWNER_EMAIL` + `VAULTWARDEN_BW_PASSWORD` |
| `vault-cli` | `ssdavidai00/alfred-vault-init:latest` | Long-running `bw serve` session on `:8087`, unlocked |

`vault-signup` is idempotent — it skips if login already succeeds *(docker-compose.yaml:707)*. The master password is auto-generated by `bootstrap.sh` and stored as `VAULTWARDEN_BW_PASSWORD` in `.env`; you can reveal it once from `/settings#agent`.

The call chain when Alfred reads a secret is:

```
claude.ai → /vaultwarden/mcp (mcp-server)
          → ctrl-api /api/v1/vaultwarden/*
            → vault-cli :8087 (bw serve)
              → vaultwarden :80
```

## The fourteen tools

The catalogue is deliberately narrow *(packages/mcp-server/src/tools/vaultwarden.ts:12–19)*. `bw serve` exposes more shapes — attachment upload, send, password history, item move, share — and every additional tool is one more attack surface from a 1-hour bearer token. The shipped subset covers safe-read + safe-write of login items, folders, and password generation.

### Status & sync

- `vaultwarden_status` — probe the bw serve session. Returns `serverUrl`, `lastSync`, `userEmail`.
- `vaultwarden_sync` — force a re-pull from the Vaultwarden server. Useful when the principal just edited an item in the web UI.

### Items: read

- `list_vault_items` — list with optional filters (search, folder, collection, organization). **Does not return passwords.**
- `search_vault_items` — POST variant for special characters in the search string.
- `get_vault_item` — fetch one item by id, **including** `login.password` and (if set) `login.totp`.

### Items: write

- `create_vault_item` — new login item. Required: `name` + `value`.
- `update_vault_item` — patch (rotate value, rename, move folder). Server-side merge.
- `delete_vault_item` — soft-delete (recoverable from the web UI's trash for 30 days).

### Folders & containers

- `list_vault_folders` — get folder ids by name.
- `create_vault_folder` — new folder.
- `list_vault_collections` — read-only; populated only if the principal set up a Bitwarden organisation.
- `list_vault_organizations` — read-only; same caveat.

### Utilities

- `generate_password` — random (default 32 chars) or diceware passphrase. Returned but **not** saved — chain into `create_vault_item({value: <returned>})` to persist.
- `vault_refresh` — the rotation primitive. See below.

## The "only app that returns passwords" rule

`get_vault_item` is the **single tool in the entire MCP catalogue** that returns secret values *(packages/mcp-server/src/tools/vaultwarden.ts:90–102)*. Every other read tool — across all six MCP apps — omits credentials. This is intentional, not accidental: it makes auditing simple, and lets policy systems gate on one method name rather than scanning every response body.

The flow Alfred uses to surface a credential:

<Steps>
  <Step title="List or search">
    `list_vault_items({search: 'wise'})` returns names + ids + folders, no passwords.
  </Step>
  <Step title="Pick one">
    The principal confirms which item. Alfred has an id.
  </Step>
  <Step title="Reveal">
    `get_vault_item({id})` returns `login.password`. The model shows the value to the principal — not the JSON envelope.
  </Step>
</Steps>

## Rotation propagation via `vault_refresh`

Updating a vault item rotates the value, but the running containers don't know. `vault_refresh` is the tool that closes the loop *(packages/mcp-server/src/tools/vaultwarden.ts:222–239)*:

```json
{ "services": ["sure-web", "sure-worker"] }
```

It rewrites `/opt/alfred/compose/.env` from the current Vaultwarden state and restarts the named services (the caller passes the list of compose service names to recreate after vault-init runs). ctrl-api refuses to restart itself, which would 502 the response mid-call.

<Warning>
The MCP catalogue is intentionally narrow because the bearer token is the entire blast radius — a leaked token can list, read, write, and delete every credential Vaultwarden holds. Rotate `MCP_APPROVAL_SECRET` from `/settings#agent` if you suspect compromise; the rotation is reveal-once and invalidates the prior secret immediately.
</Warning>
