This page collects the conventions used in Alfred Black's commit log and PR
descriptions. The rule of thumb: **the log is the design document**, so write
each entry so a contributor reading it six months later can reconstruct *why*
the change shipped, not just *what* changed.

## Commit message style

Alfred Black uses a relaxed form of [Conventional Commits](https://www.conventionalcommits.org/).
The headline is `<type>(<scope>): <short imperative summary>` — type is
mandatory, scope is strongly encouraged, and the body explains the *why* when
the headline is ambiguous.

Sample headlines from the live log (verifiable with `git log --oneline -30`):

```
feat(hermes-mcp): 6th MCP server — runtime delegation + scheduling
fix(matters): list counts.tasks ≠ detail tasks.length
feat(voice): 5 MCP servers + corresponding skills (post-rebase of #55)
fix(ctrl,hermes): consolidate skills on Hermes-canonical path
fix(integrations): Composio skill generator hits dead v2 /actions → v3 /tools
fix(compose): voice-bridge missing MCP + VOICE_* + TWILIO_AUTH_TOKEN env
```

Conventions visible from those:

- **Type vocabulary**: `feat`, `fix`, `merge`, `orchestrator`. `chore`,
 `refactor`, `style`, `docs` are not used as top-level types — they go under
 `fix` or `feat` with an explanatory scope.
- **Scope** is the package or surface: `ctrl`, `learn`, `web`, `hermes`,
 `mcp-server`, `voice`, `voice-bridge`, `compose`, `matters`, `integrations`.
 Multi-scope is comma-separated (`fix(ctrl,hermes): …`).
- **Summary** is short imperative, lower-case, no trailing period.
- **PR number** in trailing parens (`(#229)`).
- **Em-dashes** are used freely in summaries — readability over rigidity.

When the change is the result of a multi-lane fan-out:

```
merge: lane-I voice — /api/v1/channels/voice/status route + 5-case tests
merge: lane-III voice — VoiceSection (read-only deploy-readiness card)
orchestrator: wire registerVoiceRoutes() + voice-bridge compose service + voice.{$DOMAIN} Caddy
```

The `orchestrator:` prefix indicates a Phase-0 commit that touches the
forbidden zone (`server.ts`, schemas, the compose file) to stitch lane work
together. Only the orchestrator can use this prefix.

## Body — explain the *why*

For anything beyond a trivial fix, the commit body is one short paragraph
that:

1. States the bug or capability gap in one sentence.
2. Names the root cause (`file:line` where useful).
3. Says what the fix does.
4. References the related contract clause (`C-OB1`, `C14`, etc.) or issue
 number.

The standing prompt for new agents reinforces this: *"focus on the why, not
the what — the diff is the what"*. The CHANGELOG borrows liberally from
these bodies; if you write a good body, your work gets surfaced correctly in
the next release notes.

## Scope cap

By default a single PR is **at most ~200 net LOC**. The lane gate enforces
this; see [The lane gate → Scope overflow](/contributing/lane-gate#the-four-rejection-reasons).
If a logical change legitimately needs more, set `scope_limit` in `.lane` and
say so in the PR description.

<Tip>
"Logical change" means one bug, one capability, one contract clause. A PR
that hits four bugs at once is harder to review and harder to revert — split
it.
</Tip>

## PR description template

```markdown
## Summary
<1-3 bullets — what this PR ships and why.>

## Test plan
- [ ] Red test reproduces the bug before the fix
- [ ] Green test passes after the fix
- [ ] Lane VERIFY passes locally
- [ ] (If contract change) tests that asserted the old contract are updated
 in this PR
```

The "red test reproduces the bug" line is non-negotiable for fix PRs — see
[Failing-test-first](/contributing/failing-test-first).

## CI requirements

Every PR must pass `ci-check.yml` before merge. That workflow runs:

- `build-ctrl`: `npm ci` + esbuild bundle of `dist/api.mjs`.
- `pytest-learn`: `pytest` on `packages/learn/tests/` excluding slow tests.
- `compose-lint`: synthesize a dummy `.env`, run `docker compose config`.
- `bootstrap-lint`: `shellcheck scripts/bootstrap.sh`.
- `gitleaks`: secret scanning.

A red CI is a red PR. Fix the failure; don't merge around it.

## The verify gate (recap)

The lane gate's VERIFY step is the local mirror of CI:

| Lane | Local VERIFY |
|---|---|
| I — ctrl-api | `cd packages/ctrl && npm run build` |
| II — learn | `cd packages/learn && python3 -m pytest -q` |
| III — web | `cd packages/web && npx tsc --noEmit` |
| IV — alfred-vault | `cd packages/alfred-vault && python3 -m pytest -q` |
| V — edges-infra | `docker compose config -q` |

A commit cannot land locally if VERIFY fails. The emergency override
`ALFRED_SKIP_VERIFY=1` is logged in stderr — if you use it, explain why in
the PR body *(scripts/hooks/check_lane.py:120–127)*.

## Co-authorship

When a PR is generated with AI assistance, add a `Co-Authored-By:` trailer:

```
Co-Authored-By: Claude Opus 4.7 <noreply@anthropic.com>
```

The release notes group commits by author; the trailer keeps AI-assisted
contributions visible.

## After merge

- **One PR per logical change → CI builds `:latest` → deploy → smoke → next PR.**
 Never clobber a production `:latest` without verifying on a throwaway tag first.
- **Watch the deploy** — `docker compose logs -f <svc>` for two minutes after
 `docker compose up -d`. Most regressions surface in the first 90 seconds.
- **Watch the four stores** — query `state.db` and `ingest.db` after the
 deploy lands. See [Debugging guide → Common diagnostic recipes](/troubleshooting/debugging-guide#common-diagnostic-recipes).
