## Overview

Every request to the Alfred API requires a Bearer token in the `Authorization` header. The token is your tenant API key (`AAS_API_KEY`), generated by `scripts/bootstrap.sh` when your instance is provisioned. **Each token authorises one tenant — yours. The same token cannot be used to access any other instance.**

## Getting your API key

<Steps>
 <Step title="Through the dashboard">
 Sign in to your dashboard, go to **Settings → API Keys**, and create a key. The full key is shown once — copy it then. You can name keys (`my laptop`, `mobile script`, `automation`) to know which to revoke later.
 </Step>
 <Step title="Through the API itself">
 If you already have an authenticated session, `GET /api/v1/admin/credentials` returns the configured credentials with values masked. The `AAS_API_KEY` itself is protected and not modifiable through this endpoint — you can only rotate it via the dashboard.
 </Step>
</Steps>

## Token format

The token is generated at bootstrap and stored in your tenant `.env` as `AAS_API_KEY`. It is a long opaque string. Treat it as a password.

```
AAS_API_KEY=<long opaque string>
```

The dashboard may display newly created keys in a prefixed format (e.g. `alf_...`) — both forms work, the comparison is timing-safe and exact.

## Making authenticated requests

Include the key as `Authorization: Bearer ${AAS_API_KEY}`:

<CodeGroup>
```bash cURL
curl https://<your-domain>/api/v1/vault/context \
 -H "Authorization: Bearer ${AAS_API_KEY}"
```

```javascript JavaScript
const response = await fetch('https://<your-domain>/api/v1/vault/context', {
 headers: { 'Authorization': `Bearer ${process.env.AAS_API_KEY}` }
});
const data = await response.json();
```

```python Python
import os, requests

response = requests.get(
 'https://<your-domain>/api/v1/vault/context',
 headers={'Authorization': f"Bearer {os.environ['AAS_API_KEY']}"}
)
data = response.json()
```

```typescript TypeScript
import axios from 'axios';

const response = await axios.get('https://<your-domain>/api/v1/vault/context', {
 headers: { Authorization: `Bearer ${process.env.AAS_API_KEY}` }
});
const data = response.data;
```
</CodeGroup>

## How auth is checked

Caddy terminates TLS and proxies the request to `ctrl-api` on port `:3100` over the internal Docker network. The tenant's auth check is a **timing-safe constant-time comparison** against the server-side `AAS_API_KEY` — wrong keys reveal no information about the right one.

## Per-tenant scoping

Each token authorises exactly one tenant — your instance. There is no way to use your token to reach another instance's data.

Cross-tenant access exists via the `/api/v1/cross-tenant/*` endpoints (gated by environment configuration on the peer side and explicit peer listing). It does not use the same bearer flow.

## Best practices

- **Environment variables only.** Never hardcode the key. Never commit it.
 ```bash
 export AAS_API_KEY="<key>"
 curl https://<your-domain>/api/v1/vault/context \
 -H "Authorization: Bearer $AAS_API_KEY"
 ```
- **One key per use.** Name keys after their purpose (`laptop`, `n8n`, `home-assistant`) so you know which one to revoke.
- **Rotate periodically.** Create a new key, switch over, revoke the old one. The dashboard supports this without downtime.
- **Revoke unused keys.** Cleaning up shrinks the blast radius if anything is exposed.

## Error responses

A failed auth check returns 401:

<ResponseExample>
```json Missing or malformed header
{
 "error": {
 "code": "UNAUTHORIZED",
 "message": "Missing or malformed Authorization header"
 }
}
```

```json Invalid API key
{
 "error": {
 "code": "UNAUTHORIZED",
 "message": "Invalid API key"
 }
}
```
</ResponseExample>

The most common cause of `Invalid API key` is whitespace or quotes accidentally included around the token value when it was set in the environment. Strip both.

## Token rotation

To rotate without downtime:

<Steps>
 <Step title="Create a new key in the dashboard">
 **Settings → API Keys → Create**. Copy the value.
 </Step>
 <Step title="Update your clients">
 Switch every script and integration to the new key.
 </Step>
 <Step title="Verify with the health endpoint">
 `curl https://<your-domain>/api/v1/admin/health -H "Authorization: Bearer <new-key>"` should return 200.
 </Step>
 <Step title="Revoke the old key">
 Back in the dashboard, revoke the previous key. Any client still using it will start receiving 401.
 </Step>
</Steps>

## Testing authentication

The health endpoint is the lightest way to verify a token:

```bash
curl https://<your-domain>/api/v1/admin/health \
 -H "Authorization: Bearer ${AAS_API_KEY}"
```

A 200 confirms both that the key is valid and that your tenant is reachable.
