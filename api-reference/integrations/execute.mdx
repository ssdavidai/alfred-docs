## Overview

Resolves the active connection for the action's toolkit (scoped to the calling tenant), then forwards the call to the **alfred-learn Composio HTTP sidecar** at `http://alfred-learn:8788/composio/execute` *(packages/learn/src/composio_server.py)*. The sidecar holds a warmed Composio SDK client in process memory, merges any cached primary-entity [defaults](/api-reference/integrations/get-defaults) under the LLM-supplied args, runs the call in a worker thread, and returns Composio's raw result.

Before PR #177 (Phase A) this route shelled out to `docker exec alfred-learn python3 -c <script>` — every action paid ~4.5 s of Python startup + SDK import. The sidecar pays that once at process boot, so per-call latency drops to **~300–500 ms**. The route shape and response are unchanged; only the transport moved from `docker exec` to service-DNS HTTP.

This is the endpoint behind the gateway's `composio_execute` tool — every Gmail send, Calendar create, Notion update, GitHub PR create, Slack post, etc. funnels through here.

## Body Parameters

<ParamField body="action" type="string" required>
 Composio action slug, e.g. `GMAIL_SEND_EMAIL`.
</ParamField>

<ParamField body="arguments" type="object" optional>
 Action-specific arguments. The sidecar merges cached primary-entity defaults (e.g. `{calendarId: <primary>}` for `googlecalendar`) **under** these args, so an explicit `calendarId` in the request still wins. See [Get integration defaults](/api-reference/integrations/get-defaults).
</ParamField>

## Response

<ResponseField name="action" type="string">Echo of the request.</ResponseField>

<ResponseField name="toolkit" type="string">Resolved toolkit slug (derived as `action.split('_')[0].toLowerCase()`).</ResponseField>

<ResponseField name="result" type="object">
 Composio's raw response — schema varies per action.
</ResponseField>

## Request Example

<RequestExample>

```bash cURL
curl -X POST -H "Authorization: Bearer $AAS_API_KEY" \
 -H "Content-Type: application/json" \
 -d '{
 "action": "GOOGLECALENDAR_QUICK_ADD",
 "arguments": {"text": "Coffee with Miguel tomorrow at 10am"}
 }' \
 https://alfred.black/api/v1/integrations/execute
```

</RequestExample>

## Response Example

<ResponseExample>

```json 200 OK
{
 "action": "GOOGLECALENDAR_QUICK_ADD",
 "toolkit": "googlecalendar",
 "result": {
 "successful": true,
 "data": {
 "id": "abc123",
 "summary": "Coffee with Miguel",
 "start": {"dateTime": "2026-04-26T10:00:00Z"}
 }
 }
}
```

```json 400 Bad Request
{
 "error": "No active gmail connection found. Connect gmail first via the Apps page."
}
```

</ResponseExample>

<Note>
This is the canonical surface the agent reaches via `self({endpoint: "/api/v1/integrations/execute", method: "POST", body: {...}})`. Per-toolkit `alfred-composio-<toolkit>/SKILL.md` files are auto-generated on connect and tell Alfred exactly which actions exist + their args.
</Note>

<Note>
**Emergency rollback.** The `COMPOSIO_EXECUTOR=docker|http` env flag on ctrl-api preserves the old `docker exec` path for emergency rollback if the sidecar misbehaves. Default is `http`. The sidecar's health endpoint is `GET http://alfred-learn:8788/health`.
</Note>
