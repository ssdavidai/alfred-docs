## Overview

Every operation Alfred performs is exposed as an HTTP endpoint on the `ctrl-api`. The dashboard, the channels, the workflows, and the agent itself all use the same surface. This is the same API your own scripts and integrations should use.

<Note>
 Base URL: `https://<your-domain>/api/v1/...`. Authenticate every request with `Authorization: Bearer <token>`.
</Note>

## Request path

Requests reach `ctrl-api` through Caddy, which terminates TLS at your domain and proxies to the container on the internal Docker network:

```
your client
 │
 ▼
https://<your-domain> (Caddy — automatic Let's Encrypt TLS)
 │
 ▼
ctrl-api :3100 on the VM (the actual handler)
```

`ctrl-api` is the tenant's single HTTP server — vault writes, worker control, workflow management, channel dispatch all happen here.

## Versioning

The current version is **v1**. All endpoints are prefixed with `/api/v1/`. Breaking changes will move under `/api/v2/`; v1 will not silently change.

## Authentication

Every request requires a Bearer token. The token is your tenant API key (`AAS_API_KEY`, generated by `scripts/bootstrap.sh` and stored in `.env`). You can retrieve it from the dashboard under **Settings → API Keys** or via `GET /api/v1/admin/credentials`.

```bash
curl https://<your-domain>/api/v1/vault/context \
 -H "Authorization: Bearer <token>"
```

A 401 is returned for missing, malformed, or wrong tokens. See [Authentication](/api-reference/authentication) for the full flow.

<Note>
Each API key authorises **one tenant** — your instance. There is no cross-tenant access through this surface (cross-tenant tools exist via the `/api/v1/cross-tenant/*` endpoints, which go through a separate, tenant-to-tenant route).
</Note>

## Request format

All requests sending data must use `Content-Type: application/json`:

```bash
curl -X POST https://<your-domain>/api/v1/vault/inbox \
 -H "Authorization: Bearer <token>" \
 -H "Content-Type: application/json" \
 -d '{"filename": "meeting-note.md", "content": "..."}'
```

## Response format

Responses are JSON. Successful responses have an endpoint-specific shape. Errors follow:

```json
{
 "error": {
 "code": "ERROR_CODE",
 "message": "Human-readable message",
 "details": { "additional": "context" }
 }
}
```

## Error codes

| Code | HTTP | Meaning |
|------|------|---------|
| `UNAUTHORIZED` | 401 | Missing, malformed, or invalid bearer token |
| `VALIDATION_ERROR` | 400 | Request body failed validation |
| `NOT_FOUND` | 404 | The resource does not exist |
| `CONFLICT` | 409 | Operation conflicts with current state |
| `EXEC_ERROR` | 500 | Operation execution failed |
| `INTERNAL_ERROR` | 500 | Unexpected server error |

## Rate limits

There are no fixed per-second rate limits today. Your instance is dedicated, so resource pressure is a function of your own usage. Long-running operations should be triggered as workflows (`POST /api/v1/workflows`) rather than blocking on a single HTTP call.
