---
title: "Chores"
description: "The principal's recurring work, run on a Temporal schedule."
---

A **chore** is a recurring Temporal workflow the principal owns — a morning briefing, a weekly digest, a watcher that emails the principal when something specific happens. Each chore is two artifacts that stay in sync: a vault record at `chore/<slug>.md` carrying the schedule, status, and history; and a Python class under `/alfred-data/user-chores/` carrying the actual workflow code *(packages/web/src/intelligence/ChoresPage.tsx:1-6)*. The `workflow_class_name` frontmatter field on the vault record must match the `@workflow.defn(name=...)` of the deployed Python — capitalization-sensitive.

There are two surfaces:

## `/chores` — the index

The page reads `getChores` every 30 seconds and renders one row per chore *(ChoresPage.tsx:146-151)*. Each row collapses to:

- **Display name** and **category chip** (briefing, digest, watch, context-build, prefetch, maintenance)
- **Cadence** — a human-readable rendering of the cron expression (*"Daily 06:30 UTC"*, *"Mon 08:00 UTC"*) computed by `describeCron` *(ChoresPage.tsx:62-78)*
- **Last** — relative time since the last run (*"3h ago"*, *"2d ago"*, *"never"*)
- **Next** — relative time until the next scheduled fire (*"in 4h"*, *"imminent"*)
- A one-line **description** pulled from `display_body` / `user_facing_description`

Expanding a row reveals the full description plus four actions, each calling its corresponding Wasp operation:

| Action | Wasp op | What it does |
|---|---|---|
| **Pause** | `pauseChore({ slug })` | Sets the chore's Temporal schedule to paused; status flips to `paused`. |
| **Resume** | `resumeChore({ slug })` | Re-enables the schedule. |
| **Run now** | `triggerChore({ slug })` | Fires the workflow immediately, out-of-schedule. The next cron fire still happens on its normal cadence. |
| **Delete** | `deleteChore({ slug })` | Stops the schedule and unregisters the workflow. The vault record stays so run history is preserved. |

A **+ New chore** affordance opens a text panel — the principal describes the chore in prose; the request is dropped into the triage pipe as a `triage` record with `intent: chore_request`, and the curator / chore-generator workflow picks it up to materialise the code and schedule *(ChoresPage.tsx:208-225)*.

A **category filter** above the rows derives its facets from the chores actually present on the tenant *(ChoresPage.tsx:161-163)*. The `/dashboard/tasks` alias resolves here.

## `/chores/:slug` — the detail page

`ChoreDetailPage2` is the per-chore view. Top to bottom *(packages/web/src/intelligence/ChoreDetailPage2.tsx:1-16)*:

1. **Header** — name, status pill, schedule line, the same Pause / Resume / Delete / Run now buttons
2. **What this chore does** — `display_body` or fallback description body
3. **Readiness / audit** — an anti-hallucination view from `getChoreSource`: verdict, unknown-activity warnings, and per-activity manifest cards (each activity declares what it `reads` and `writes`, and the readiness check flags `ok` / `empty` / `missing` / `untested`)
4. **Run history** — parsed `## Run log` entries from the vault body, plus `last_run` / `last_result`
5. **Living state** — `current_state` + `as_of` + timeline (hidden when empty, rather than lying about future composition)

The schedule editor uses `getChoreScheduleFires` to render a cron preview before any change is saved through `patchChore`. The page deliberately does **not** show a stage tier; chores are recurring schedules, not lifecycle objects.

## The 3-run quarantine

Every chore generated by the system enters service with `quarantine: true` and `quarantine_remaining: 3` *(packages/learn/src/activities/assign_chores.py:427-428)*. The first three fires are **dry-runs** — the workflow loads its context as normal, but the quarantine gate makes it return early without writing to the vault, sending notifications, or saving snapshots *(packages/learn/src/activities/chore_generation_prompts.py:191)*.

Each dry-run decrements `quarantine_remaining`. After three the quarantine clears automatically and the chore goes live on the next cron fire.

The principal sees this on `/chores` as a small **`Quarantine 2/3`** badge next to the chore name *(packages/web/src/intelligence/ChoresContent.tsx:297-328)*, plus a generation note in the expanded row: *"First N runs will be dry-runs (no notifications, no vault writes) so we can verify behavior before going live."*

<Note>
The quarantine is the first 3 *runs*, not the first 3 days. A chore that runs hourly clears quarantine in three hours; a weekly chore takes three weeks. *Run now* fires count toward the quarantine just like scheduled fires, so the principal can deliberately clear it by running the chore three times in succession.
</Note>

<Tip>
After 20 live runs at ≥95% success, the weekly `ChorePromotionReflectionWorkflow` (Sundays 03:00) drafts a GitHub PR to promote the chore from the user-chores directory into the bundled chore set — moving a tenant-specific pattern into the shared catalogue.
</Tip>
