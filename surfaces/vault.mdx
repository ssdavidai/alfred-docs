`/vault` is the only place in the UI where the principal reads and edits raw vault records. The page is a three-pane Obsidian-style layout — tree on the left, reader/editor in the middle, backlinks on the right — bookmarkable by `?slug=<vault-path-without-.md>` *(packages/web/src/dashboard/VaultPage.tsx:1-24)*.

## The three panes

**Tree (left).** Renders `getVaultGraph` nodes grouped client-side into four families: **Standing** (person, org, project, matter, asset, …), **Activity** (task, conversation, note, chore, event, signal, …), **Learning** (assumption, decision, constraint, synthesis), **Intuition** (observation, instinct, reflection, pattern_proposal) *(VaultPage.tsx:65-100)*. The free-text search filters across name, path, and type; expanding a family expands its types, and each type lists its records alphabetically.

**Reader / editor (middle).** Reads `getVaultRecord({ path })` and renders the body through the shared `Markdown` component (which wires `getVaultTitleIndex` so `[[wikilinks]]` resolve live). The *Edit* button swaps into a textarea over the body plus, for `matter/*` and `task/*` records, an explicit **State fields** panel above it.

**Backlinks (right).** Derived from `getVaultGraph` edges where `target` equals the open record's path, grouped by source type — *Linked from · person, org, task, …* *(VaultPage.tsx:199-212)*.

A *+ New record* affordance opens an inline dialog (type select + name input) and calls `createVaultRecord`. The slug is normalised — lowercased, non-alphanumerics collapsed to dashes — before the write.

## Two distinct save paths

Edit mode does not save with a single PATCH. It diffs the principal's draft against the snapshot the editor mounted with and **routes state-field changes through a different endpoint** than body or non-state frontmatter changes *(VaultPage.tsx:320-394)*.

<Tabs>
 <Tab title="State fields → applyManualStateChange">
 For `matter/*` records the declared state fields are `current_state`, `as_of`, `status`, `surface_class`, `last_briefing_at` *(VaultPage.tsx:40-46)*. For `task/*` they are `current_state`, `as_of`, `status`, `outcome`, `pending_confirmation`, `last_steward_outcome` *(VaultPage.tsx:48-55)*.

 A change to any of these fires `applyManualStateChange({ target_path, fields, expected_as_of, reason })` which POSTs to `/api/v1/state-changes`. The server attaches `source=manual.<userId>`, `confidence=1.0`, `mode=live`, and writes a row to `alfred-state.db.state_change` **plus** patches the frontmatter on disk. The audit trail is durable and queryable from `/decisions` State Changes tab.
 </Tab>
 <Tab title="Body & non-state fm → createVaultRecord">
 Body edits (and any frontmatter the editor does not flag as a state field) are wrapped into a full file blob (`buildContent`) and POSTed through `createVaultRecord` — the same endpoint used by *+ New record*, which upserts on POST. The frontmatter is recomposed from the mounted snapshot so this path never re-PATCHes a state field through the legacy endpoint; ctrl-api has already bumped `as_of` if a state-change envelope ran *(VaultPage.tsx:364-382)*.
 </Tab>
</Tabs>

## The `as_of` fence and the 409 dialog

`applyManualStateChange` carries `expected_as_of: mountedFm.as_of` — the value the editor read at mount time. ctrl-api treats this as optimistic concurrency: if another writer bumped `as_of` while the editor was open, the request returns **HTTP 409** *(VaultPage.tsx:343-360)*.

The page catches that response and renders a modal:

- **Reload** — drop the local edits and re-read `getVaultRecord`. The editor reopens against the fresh `as_of`.
- **Force write** — re-submit with `expected_as_of: null`, skipping the fence and writing through. This is the only path that ever omits the fence.

<Warning>
The Vault editor is the **only UI surface** that writes vault records directly. Every other surface goes through a typed endpoint (the desk decision cascade, the matters detail edits, etc.). If you find yourself writing a new vault file from another page, prefer the typed route — it picks up the promotion-contract check, the state-change envelope, and the indexing pass for free.
</Warning>

## What this page does not do

- It does not enforce permissions; the auth layer at `wasp/server` covers that.
- It does not pretty-print frontmatter — the *Details* `<details>` panel above the body shows type, family, created, status, tags, and slug in a monospace grid *(VaultPage.tsx:623-647)*.
- It does not delete records. Demoting a record off the vault is a separate operation done from a record-type-specific surface (matters detail, chores detail) or via the ctrl-api directly.
